# /bug-complete

수정이 검증된 버그의 문서를 정리하고 닫는다. 코드는 건드리지 않는다.

## 입력

- `BUG-NN` (+ phase, 애매하면).

## 절차

1. **검증 확인**: `/bug-execute`가 테스트를 통과시켰는지, UI 버그면 사용자가 브라우저에서 확인했는지 재확인한다. 확인이 안 됐으면 먼저 확인부터 받는다(자동으로 완료 처리하지 않는다).
2. **전부 고쳐졌는지 판단**:
   - **전부 고쳐짐** → 3번으로.
   - **일부만 고쳐지고 나머지는 보류/분리** → `BUG-NN-*.md`를 고쳐진 부분만 빼고 다시 써서 `bugs/` 폴더에 남긴다(남은 문제의 증상/보류 사유를 명확히). 고쳐진 부분만 아래 3번으로 옮긴다.
3. **fixed 문서 작성**: `.planning/fixed/`가 없으면 만든다. `.planning/fixed/{padded_phase}-{NN} 간단한 정리.md` 이름으로 아래 형식으로 쓴다(기존 예시: `08-04 사고 토큰 차감 누락 수정.md`, `04-02 멘션 자동완성 키보드 선택 수정.md` 참고).

   ```markdown
   ---
   id: {phase}-{NN}
   title: <한 줄 제목>
   fixed: <YYYY-MM-DD>
   files:
     - <관련 파일 경로>
   ---

   # {phase}-{NN}: <제목>

   ## 증상
   ## 원인
   ## 수정
   ## 검증
   ## 커밋
   ```

4. **원본 삭제/갱신**: 전부 고쳐졌으면 `bugs/BUG-NN-*.md`를 삭제한다. 그 phase의 `bugs/README.md` 표에서 해당 행을 지우고(또는 상태를 갱신), 다른 README/STATE.md 등에서 이 버그를 참조하던 링크·상태 문구가 있으면 같이 갱신한다.
5. **커밋**: 문서 변경만 별도 커밋으로 만든다(코드 커밋과 분리 — `/bug-execute`가 이미 코드를 커밋했으므로). 메시지 예: `docs({phase}): BUG-NN <제목> 완료 정리`.
6. **보고**: 무엇이 `fixed/`로 옮겨졌는지, 남은 게 있으면 무엇인지 사용자에게 요약한다.
