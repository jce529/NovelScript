# /bug-execute

`/bug-plan`이 만들어 둔 버그 문서의 "수정 방향"을 실제로 구현한다.

## 입력

- `BUG-NN` (필요하면 phase도 — 같은 번호가 다른 phase 폴더에도 있을 수 있으므로 애매하면 경로까지 명시하게 한다).

## 절차

1. **문서 로드**: `.planning/phases/{phase}/bugs/BUG-NN-*.md`를 전부 읽는다(증상/원인/수정 방향/검증).
2. **미결 정책 확인**: "수정 방향"에 옵션(A/B/C)만 있고 아직 확정되지 않았으면 여기서 멈추고 사용자에게 묻는다. 임의로 하나를 골라 진행하지 않는다.
3. **구현**: 문서의 수정 방향대로 코드를 고친다. 범위를 벗어나는 리팩터링·기능 추가는 하지 않는다(버그 수정에 집중).
4. **테스트**: 문서의 "검증" 절에 적힌 대로 테스트를 추가/갱신한다. 실패하는 재현 테스트가 먼저 있었다면 그것부터 통과시킨다.
5. **검증 실행**: 관련 테스트 스위트 + 타입체크(`tsc --noEmit` 또는 프로젝트의 동등 명령)를 실행해 전부 통과할 때까지 반복한다. UI 변경이면 <when_to_verify> 관례에 따라 브라우저로 확인한다.
6. **문서 갱신**: `BUG-NN-*.md`에 실제 적용한 변경 내용을 "수정 방향" 아래 덧붙이거나 별도로 기록해 둔다(아직 `status: open`으로 유지 — `/bug-complete`가 최종 정리한다). 부분적으로만 고쳤다면(일부는 보류) 어느 부분이 남았는지 명확히 적는다.
7. **커밋**: 코드 변경 + 테스트를 하나의 커밋으로 만든다. 문서 재구성(폴더 이동 등)은 여기서 하지 않는다 — `/bug-complete` 몫이다. 커밋 메시지 예: `fix({phase}): BUG-NN <제목>`.
8. **보고**: 무엇을 고쳤는지, 테스트 결과, 커밋 해시를 사용자에게 요약하고 `/bug-complete`로 넘어갈지 확인한다.
