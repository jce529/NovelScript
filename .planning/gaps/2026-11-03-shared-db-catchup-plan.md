# 공유 DB 따라잡기 계획 (2026-11-03)

> 상태: **리허설 준비 단계 — 공유 DB(`ymudwg…`)에는 아무것도 적용하지 않았다.** 2026-11-03 사용자가 STATE의 "적용 금지"를 해제했고(리허설 통과 후 정지점마다 승인으로만 적용), 리허설용 새 Supabase 프로젝트를 기다리는 중이다.
>
> **리허설 환경 (결정: 새 빈 프로젝트에 공유의 현재 스키마를 재현):** 이 PC에는 `pg_dump`·`psql`·Docker·Supabase CLI가 없어 공유 데이터 복제가 어렵다. 새 프로젝트에 공유와 같은 상태(0001~0021 + 0028)를 재현한 뒤 delta를 적용한다. 실제 데이터 위의 0022 백필은 Supabase "Restore to new project"(유료 플랜)로 복원한 프로젝트가 있을 때만 검증할 수 있고, 없다면 합성 픽스처로 대체하며 그 한계를 기록한다.
>
> 도구: `node scripts/apply-pending-migrations.mjs` (기본 dry-run, `--execute --env-file --expect-ref`, 공유 ref는 `--allow-shared` 없이는 거부, `--stop-after`로 정지점).
> - 기준선 재현: `--from 0001 --to 0021` 뒤 `--from 0028 --to 0028`
> - delta: `--from 0022 --to 0039 --skip 0028,0031 --stop-after 0023,0030,0036`
> 근거: 2026-11-03 읽기 전용 점검(`shared-db-preflight.cjs`, 모든 쿼리 READ ONLY). 이 문서는 시점 스냅샷이다.

## 4. 단계

### 0. 준비 (읽기·백업만)
- [ ] 백업 확보: Supabase 대시보드 Database → Backups(PITR 여부 확인) 또는 `pg_dump` 전체. **이 게이트를 통과해야 다음으로 간다.**
- [ ] 점검 스크립트 출력과 함수 스냅샷을 날짜와 함께 보관.

### 1. 리허설 (공유 복사본에서)

- [ ] 마지막에 DB 테스트: `READING_STATE_DB_TEST=1 COMPLETION_DB_TEST=1 WTREE_BRANCH_RACE_SCHEMA_COMMIT=1`로 `tests/mcp --project db` 포함 DB 스위트를 skipped 0으로 실행. 환경변수는 프로세스로 고정하고 ref를 먼저 확인한다(STATE의 "실행 시 주의").

### 2. 공유 적용

- [ ] 점검 스크립트 재실행: 전부 n/n, `oauth_browser_only` 정책 수·가드 함수 수 기록.

## 8. 리허설에서 발견한 공유 DB 드리프트 (2026-11-03)

일회용 DB를 공유와 같은 기준선(0001~0021 + 0028)으로 재현해 함수 정의를 비교한 결과, 57개 중 54개가 같고 3개가 달랐다.

| 함수 | 공유 DB 상태 | 위험 | 처리 |
|---|---|---|---|
| `soft_delete_kb_node(uuid, uuid)` | 0008의 쓰기 권한·소유자 확인(`write_access_denied`, `p_owner_id` 비교)이 없는 이전 정의. SECURITY DEFINER, `authenticated` 실행 가능 | 호출자가 노드 ID와 소유자 ID를 알면 남의 KB 노드를 soft delete 할 수 있다. ID가 비공개 UUID라 실제 악용은 어렵지만 결함이다 | 이후 어떤 마이그레이션도 다시 정의하지 않으므로, 0008의 최종 정의를 `create or replace`로 다시 적용하는 단계가 필요하다(별도 마이그레이션 번호로, 일회용·리허설에는 이미 같은 정의라 무해) |
| `get_byok_secret_with_id(uuid, text)` | 공유에만 있음. 저장소·git 히스토리에 없다(수동 생성 추정). 복호화된 BYOK 키 반환 | 실행 권한이 `postgres`와 `service_role`뿐(`anon`·`authenticated` 불가)이라 브라우저 사용자에게는 노출되지 않는다 | 그대로 둔다. 배포된 앱이 쓰는지 확인하기 전에는 삭제하지 않는다 |
| `mark_byok_key_failed(uuid, text, uuid)` | 공유에만 있음, 같은 권한 | 위와 동일 | 위와 동일 |

- 함수 외 객체(정책·트리거·제약·인덱스·컬럼·권한)는 아직 비교하지 않았다. 마이그레이션 파일이 적용 후 수정된 흔적이 있어, 리허설 기준선을 다시 만든 뒤 공유와 지문 비교를 추가로 한다.
- 이 드리프트는 "공유 DB는 저장소의 0001~0021·0028과 정확히 같지 않다"는 뜻이라, 리허설이 통과해도 공유 적용 전에 이 차이를 별도로 메워야 한다.
