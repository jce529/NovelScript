# BUG-04: 사고(thinking) 토큰이 maxOutputTokens 예산을 잠식해 본문이 잘림

> 원래 BUG-04는 "차감 누락 + 출력 잘림" 두 문제를 함께 다뤘다. 차감 누락은
> 2026-09-22에 수정 완료되어 [`.planning/fixed/08-04 사고 토큰 차감 누락 수정.md`](../../../fixed/08-04%20사고%20토큰%20차감%20누락%20수정.md)로

## 정책 정리 (2026-10-04) — 결정 상태 한눈에 보기

이 문서·`17-CONTEXT.md`·`11-CONTEXT.md`에 흩어진 BUG-04 관련 결정을 한곳에 모았다. 새 결정은 없다. **단계 B(정책)는 사용자 결정 대기다.**

### 문제 두 겹
1. **표시 오류(확정·수정 대상):** `wasCapped = (finishReason === 'max_tokens')`가 잔액 캡 / 요청당 상한 / thinking 소진을 구분하지 못해, 잔액이 충분해도 "토큰이 모두 소진됐어요"가 뜬다 (`lib/ai/chat.ts`, `lib/ai/document-plan.ts`). 2026-10-02 UAT 근거: 잔액 10954·Gemini 3.5 Flash에서 짧은 요청이 `max_tokens`로 끝남(원장 -4). 이 근거는 단일 관찰이라 빈도 판단에는 약하다.
2. **예산 정책(미결):** `maxOutputTokens`가 사고+본문 합계라서 사고가 길면 본문이 잘린다. 현재 `thinkingConfig` 미설정, 상한은 `min(잔액 환산, 2048)` (`lib/ai/cost.ts`). 차감은 `candidates + thoughts` 합산으로 정상이다(회귀 없음, `fixed/08-04`).

### 권고 (확정 아님)
단계 A를 Phase 17에서 먼저 처리하고, 후보 4는 **관측 로그 추가 → 실키 A/B → 채택 여부 결정** 순으로 간다. 이유: 품질 영향을 데이터 없이 판단하지 않는다는 2026-09-22 보류 원칙을 유지하면서, 사용자에게 보이는 오표시는 바로 고칠 수 있다.

### 의존 관계
- **Phase 11:** `preflightPaidGeneration`/`settlePaidGeneration` 공통 경로를 수정한다. 후보 4의 상한 계산(`cost.ts`)과 같은 영역이라 Phase 11 이후에 구현하면 BYOK 분기와 두 번 겹쳐 고치지 않아도 된다.
- **Phase 17 (BUGFIX-01):** 단계 A 실행처. 성공 기준 1("잔액이 충분하면 '토큰 소진' 문구가 나오지 않는다")이 단계 A를 요구한다.
- **미확인:** 사용 모델 ID별 `thinkingBudget`/`thinkingLevel` 지원, 예산이 엄격한 상한인지, 최소 사고량(끌 수 없는 모델)이 있는지.

## 증상

`maxOutputTokens`는 Gemini에서 "사고 토큰 + 본문 토큰"의 합계에 적용된다. 사고가 길면 본문이 그만큼 짧아지거나 아예 잘릴 수 있다(`finishReason: max_tokens`).

## 측정 (2026-09-18, lite, 한국어 지문 3개) — 참고용, 대표성 낮음

| 입력 토큰(보고) | 출력 토큰(보고) | 사고 토큰(보고) |
|---|---|---|
| 90 | 11 | 241 |
| 98 | 7 | 245 |
| 209 | 6 | 246 |

이 측정은 `maxOutputTokens: 256`으로 강제한 임시 실험 3건뿐이며, 실제 서비스에서는 잔액에 따라 훨씬 큰 상한(최대 2048)이 걸린다. KB 멘션이 포함된 정상적인 생성 트래픽에서 사고 토큰이 얼마나 쓰이는지는 별도로 관측된 바 없다.

## 결정 보류 사유 (2026-09-22 사용자 논의)

사고 예산(`thinkingConfig.thinkingBudget`)을 인위적으로 줄이면 비용/잘림은 줄지만 문체 일관성·설정 반영 같은 생성 품질이 나빠질 수 있다. 실사용 데이터 없이 지금 트레이드오프를 판단하지 않기로 하고, 다음 관찰 후 재논의하기로 함:
- 실사용에서 `wasCapped`(잘림) 발생 빈도
- 사고 예산을 줄였을 때 실제 품질 차이 (A/B 비교 필요)

## 해결 방향 후보 (미확정)

- 사고 예산을 고정값(예: 512)으로 제한해 본문 공간을 확보 — 품질 영향 미검증.
- 상한 자체를 올려서(잔액이 허용하는 한) 사고+본문 모두 여유를 주는 방식 — 차감액이 커지는 부작용.
- 현행 유지 — 관찰만 계속.

- **후보 4 (2026-10-03 논의, 유력): 사고 몫과 본문 몫 분리.**
  - 사고 상한 `T`와 본문 보장 몫 `B`를 따로 두고 `maxOutputTokens = T + B`로 계산한다. API에는 별도 본문 상한 파라미터가 없으므로 `T`는 Gemini `thinkingBudget`(2.5 계열)/`thinkingLevel`(3 계열)로 묶고, 합계 상한으로 본문 `B`를 확보한다.
  - 잔액이 `T + B`보다 적으면 `B`를 먼저 보장하고 남는 만큼만 `T`로 준다(사고가 잔액 전부를 먹는 경우 방지).
  - `T`는 코드 상수가 아니라 설정값으로 둔다. 문체·설정 반영 품질 영향은 키가 있는 환경에서 A/B로 조정한다(기존 보류 사유 유지).
  - 제공사별 번역: Gemini는 위와 같음, Anthropic 구형은 `budget_tokens`(최신 모델은 `effort`만), OpenAI는 숫자 상한 없이 `reasoning_effort` 수준으로만 가능 → 어댑터별 번역 필요.
  - 차감은 현행처럼 `candidates + thoughts` 합산 유지(`lib/ai/cost.ts:37`), 변경 지점은 `lib/ai/cost.ts` 상한 계산과 `lib/ai/providers/gemini.ts` `config`.
  - 사고가 `T`에 닿은 것은 잘림이 아니므로 "토큰이 모두 소진됐어요" 안내는 본문 `B`나 잔액 한도에 닿은 경우로 한정(Phase 17 성공 기준 1과 연결).
  - 확인 필요: 사용 모델 ID별 `thinkingBudget`/`thinkingLevel` 지원과 예산이 엄격한 상한인지, 최소 사고량(끌 수 없는 모델)이 있는지.

## 후보 5: 작가 조절형 사고·본문 한도 (2026-10-07 제안, 미확정)

> 제안 배경: 2026-09-19 Phase 9 옛 CONTEXT(삭제본, `git show b908bba^:.planning/phases/09-openai-anthropic-adapters-pricing/09-CONTEXT.md`)의 결정 D-11(사고 끔/최소)·D-12(사고 토큰 출력 단가 차감)·D-05~D-09(비용 표시)가 현행 Phase 9 CONTEXT(2026-09-22)에서 빠졌다. 추적 결과 D-12(차감)는 구현됨, D-11(사고 끔/최소)과 D-07(글자수 기준 비용 표시)은 코드·문서 어디에도 없다. 이를 한 기능으로 묶는 안이다. 결정된 바 없다.

### 구조
- **사고 강도 = 단계식** (끔 / 낮음 / 보통 / 높음). 어댑터가 제공자별 값으로 번역한다. 기본값은 "끔" 또는 모델이 허용하는 최소(= 옛 D-11).
- **본문 한도 = 게이지 슬라이더.** 후보 4의 본문 보장 몫 `B`를 작가가 정한다. 모든 제공자에서 호출 상한으로 지킬 수 있다.
- 호출 상한 `maxOutputTokens = B + T(단계)`. 잔액이 부족하면 `B`를 먼저 보장하고 남는 만큼만 `T`(후보 4와 동일).
- **비용 표시:** 설정이 바뀔 때마다 "최대 N토큰까지 차감"을 보인다(옛 D-07의 글자수 환산 대신 상한 기준). 차감은 현행처럼 실사용량 합산(`candidates + thoughts`), 사고 토큰은 출력 단가(= 옛 D-12, 구현 완료).

### 사고 토큰을 슬라이더로 하지 않는 이유
세 제공자가 지원하는 조절 방식이 달라 "한도를 지킨다"고 약속할 수 있는 단일 UI가 단계식뿐이다.
- Anthropic: `budget_tokens`로 토큰 수 지정 가능하나 최소값 제약이 있고 `max_tokens`보다 작아야 한다. 최신 모델은 `effort`만 지원한다는 기록이 있다(위 후보 4).
- Gemini: 2.5 계열 `thinkingBudget`(토큰 수), 3 계열 `thinkingLevel`(단계). 모델 세대별로 다르다.
- OpenAI: `reasoning_effort` 단계만 있고 사고 토큰 상한 파라미터가 없다. 전체 `max_output_tokens`만 걸 수 있다.
→ 사고 토큰 슬라이더는 OpenAI에서 "대략의 희망치"일 뿐 한도가 아니다.

### 주의 · 미확인
- **새 기능 규모**다. 버그 수정이 아니라 별도 phase(또는 Phase 17 이후 backlog)로 다룰지 결정이 필요하다. 9/19 문서가 이미 "별도 페이즈"로 미뤘다.
- 후보 4와 마찬가지로 **관측 → 실키 A/B** 가 선행 조건이다. 사고를 끄면 문체·설정 반영 품질이 떨어질 수 있다는 보류 사유(2026-09-22)는 유효하다.
- **F만 먼저**: 사고 "끔/최소" 기본값은 UI 없이 어댑터 설정만으로 넣을 수 있다. 다만 후보 4의 품질 우려와 같으므로 이것도 사용자 결정이 필요하다.
- 모델별로 사고를 끌 수 있는지, 끌 수 없는 모델의 최소 사고량이 얼마인지는 미확인이다(리서치 필요, 담당 모델은 Haiku 지정).
- 계정 기본값 저장 위치(`/studio/settings/ai-providers`, 현행 Phase 9 D-04)와 BYOK 경로 적용 여부(위 결정 필요 3번)가 함께 걸린다.
- 관련 별도 건(이 기능과 무관, 미문서화): 서비스 키 없는 제공자 모델이 목록에 노출됨(옛 D-03), 기본 모델 대체 시 패널 안내 없음(옛 D-10c). 둘 다 Haiku 조사 기준이며 코드 직접 확인은 아직 안 했다.
