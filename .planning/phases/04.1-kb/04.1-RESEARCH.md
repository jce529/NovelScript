## Summary

This phase is **not** a new-technology integration — it's a schema/architecture extension of the exact `kb_nodes` adjacency-list design Phase 2 shipped (`supabase/migrations/0002_studio.sql`), plus one deliberate **bug-fix regression** the phase must also correct along the way (see below). No new npm packages are needed.

Reading the actual running code (not just CONTEXT.md's description of it) surfaced three load-bearing facts that materially shape the plan:

1. **`kb_nodes.category` already does double duty** as both "this folder's structural type" and "this file's inherited document type" — `components/studio/kb-node-dialogs.tsx`'s `CreateNodeDialog` always passes `category={node.category}` (the parent's own category) when creating a child, so category silently propagates down the tree with zero special-casing today. This means the cleanest way to support KB-03's arbitrary custom folders is to **add exactly one new sentinel value (`'custom'`) to the existing CHECK constraint** and let it propagate through the exact same mechanism — no new column, no new propagation logic.

2. **Phase 2's locked-folder decision (D-15: "6 structural folders are fixed") never actually shipped.** `0002_studio.sql`'s `create_work()` only sets `is_locked = true` for the `template` category; a trailing `UPDATE` statement in the same migration explicitly force-unlocks `인물/장소/사건/세력/아이템` ("seeded locked by mistake"). `tests/studio/schema-smoke.test.ts` codifies this as *current expected behavior* ("only the template folder locked" / "인물/장소/사건/세력/아이템 are unlocked"). **04.1-CONTEXT.md's D-03 re-asserts that all 7 structural folders (including the new 회차) must be locked** — so this phase must both (a) lock the 5 previously-unlocked category folders for all existing works, and (b) update the now-incorrect test assertions in `schema-smoke.test.ts`. This is a real, actionable finding, not a hypothetical — skipping it means KB-05 ships with a known-broken lock guarantee.

3. **회차 (chapters) are structurally invisible to the KB tree today** — `app/studio/[workId]/layout.tsx` renders `ChaptersNavLink` (a pinned link to `/studio/[workId]/chapters`) **completely separately from** `KbTree`, and `getKbTree()` never touches the `chapters` table. Folding 회차 into the same visual tree (KB-05) requires a UI-layer merge (chapters fetched separately, attached as synthetic leaf nodes under their 회차-category folder) — `chapters` stays its own table/RLS/Server-Actions per D-05, only a new nullable `chapters.folder_id → kb_nodes.id` column is added for grouping.

**Primary recommendation:** One migration (`0004_kb_custom_folders.sql`) that (a) widens the `category` CHECK to add `'회차'` and `'custom'`, (b) adds `회차` as a 7th locked folder in `create_work()` + backfills existing works, (c) fixes the 5-folder lock regression for existing + future works, (d) adds `chapters.folder_id uuid references kb_nodes(id)` (nullable = "at 회차 root"), (e) adds a guard trigger blocking generic KB *file* nodes from being created under any `category = '회차'` folder. Both roots (작품 폴더, 계정 공유 폴더) stay **implicit UI containers, not new `kb_nodes` rows** — this exactly matches how 작품 폴더 already works today (it's just `work.title` rendered as a header above the tree; there is no "work root" `kb_nodes` row), so 계정 공유 폴더 gets the same treatment for consistency and to avoid an unnecessary reparenting migration.

## Architecture Patterns

### §1. `category` CHECK constraint — concrete change

**Current constraint** (`supabase/migrations/0002_studio.sql:28`):
```sql
category text not null check (category in ('template','인물','장소','사건','세력','아이템'))
```

**Decision: widen to 8 values, do not restructure the column.**
```sql
alter table kb_nodes drop constraint if exists kb_nodes_category_check;
alter table kb_nodes add constraint kb_nodes_category_check
  check (category in ('template','인물','장소','사건','세력','아이템','회차','custom'));
```
*(Confidence note: `kb_nodes_category_check` is Postgres's default auto-generated name for an inline `check()` on the `category` column with no explicit constraint name — this is standard Postgres naming behavior, HIGH confidence. Still recommend the executor verify with `\d kb_nodes` or `select conname from pg_constraint where conrelid = 'kb_nodes'::regclass` before relying on the literal name, since `DROP CONSTRAINT IF EXISTS` degrades gracefully either way.)*

**Why `'custom'` as a single sentinel (not a free-text category):**
- `category` already propagates from parent → child with zero extra logic today (`CreateNodeDialog` passes `category={node.category}` verbatim). Reusing this exact mechanism for custom folders means **no new propagation code is needed** — a custom folder's `category` is `'custom'`, and any file/subfolder created inside it inherits `'custom'` the same way a file inside `인물/` inherits `'인물'` today.
- The one new branch needed: when creating a folder **directly under a root** (work root or account-shared root — i.e. `parent_id` resolves to nothing, since roots aren't real rows, see §2), there is no parent category to inherit, so the new folder gets `category = 'custom'` explicitly. This is the only place category must be assigned rather than inherited.
- `category = '회차'` is assigned the same way: the fixed 회차 root folder gets `category = '회차'` at seed time (§3), and its user-created sub-folders (arcs) inherit `'회차'` — this is deliberate (see §7's guard trigger: it lets the DB cheaply identify "is this folder part of the chapters tree" via `category = '회차'` without walking `parent_id` ancestry, since `ancestor_ids`/`depth` columns exist in the schema but are **never populated by any current code path** — confirmed via repo-wide grep, they are dead columns at their `'{}'`/`0` defaults. Do not rely on them for ancestry checks in this phase.)

**Existing query sites unaffected by this change** (verified by reading each): `kb_nodes_work_category_idx`, `resolveCategoryFolderId` (mentions.ts, only ever looks up the 5 fixed `KbCategory` values), `resolveTemplateOverride`/`listTemplateOptions` (only ever look up `category = 'template'`). None of them need to change to accommodate `'custom'`/`'회차'`.

### §2. Account-shared root materialization — decision: implicit, no new row

**Finding:** 작품 폴더 (work root) is **already** implicit today — there is no `kb_nodes` row representing "the work root." `app/studio/[workId]/layout.tsx` renders `work.title` as a plain header `<div>`, then `KbTree` renders every `parent_id = null, scope = 'work'` node as a top-level list item beneath it. D-02's "cannot create a new root or rename/delete an existing one" is satisfied for 작품 폴더 today simply because there's no row to act on.

**Decision:** apply the exact same treatment to 계정 공유 폴더 — **do not materialize a new `kb_nodes` row for it.** Render it as a second fixed section header in the same sidebar (e.g. `계정 공유 폴더` label, styled distinctly, not a `Link`/clickable tree row), with its own `KbTree`-style list of `parent_id = null, scope = 'account_template'` nodes underneath.

**Why not materialize a row (rejected alternative):** the alternative — insert one `kb_nodes` row (`scope='account_template', parent_id=null, category='account_root'`) and reparent the existing `template` folder under it — requires (a) a new CHECK sentinel value, (b) a one-time data migration reparenting the existing `template` row's `parent_id` for every current account (touching live data with no functional upside), and (c) introduces an asymmetry where 작품 폴더 has no row but 계정 공유 폴더 does, for no benefit — `buildTree`/`TreeNode` already handle a flat list of multiple `parent_id = null` roots correctly (confirmed: `buildTree`'s "orphan/no-parent → treated as root" behavior, `tests/kb/tree-query.test.ts`'s "merges... each tagged by scope" test already exercises exactly this multi-root shape). Implicit wins on both simplicity and consistency.

**Required refactor this implies:** `getKbTree()` currently **merges** work-scoped and account-scoped nodes into one flat array and `WorkLayout` calls `buildTree()` **once** on the merged list — meaning today the account-level `template` folder renders as a top-level sibling mixed in among the work's own 회차/인물/장소/... folders (distinguished only by a "계정 공용" badge). To match D-01's explicit two-section diagram, split this:
```typescript
// lib/kb/actions.ts — split getKbTree's two queries into two exported functions
// (or return { workNodes, accountNodes } instead of one merged array)
export async function getWorkKbNodes(supabase, { ownerId, workId }): Promise<FlatKbNode[]> { /* existing workNodes query only */ }
export async function getAccountSharedNodes(supabase, { ownerId }): Promise<FlatKbNode[]> { /* existing accountNodes query only */ }
```
```typescript
// app/studio/[workId]/layout.tsx — two separate buildTree() calls, two separate <KbTree> renders
const workTree = buildTree(await getWorkKbNodes(supabase, { ownerId: user.id, workId }));
const accountTree = buildTree(await getAccountSharedNodes(supabase, { ownerId: user.id }));
// render: work.title header + <KbTree nodes={workTree}/>, then "계정 공유 폴더" header + <KbTree nodes={accountTree}/>
```
This is a **breaking behavior change to existing, tested code** (`tests/kb/tree-query.test.ts`'s `getKbTree` test asserts the merged-array shape) — flag as a required test update, not just new-code addition.

### §3. Chapter-folder grouping schema — decision: nullable FK on `chapters`

**Decision:**
```sql
alter table chapters add column if not exists folder_id uuid references kb_nodes(id);
create index if not exists chapters_folder_idx on chapters (folder_id) where deleted_at is null;
```
- `folder_id IS NULL` = "directly at 회차 root" (no sub-folder). This is deliberately the **default/no-migration-needed** state — every existing chapter naturally satisfies D-06's "no orphaned chapters" requirement the moment the 회차 root folder itself is backfilled (§7), with zero per-chapter data migration needed.
- **Rejected: join table.** D-05 frames this as "which sub-folder, if any, a chapter belongs to" — a single-parent (not many-to-many) relationship. A join table would model a relationship that can't occur in this UI (no multi-folder chapter membership is requested), adding join complexity for no behavioral gain.
- **Rejected: folder-only `kb_nodes` rows referenced FROM `chapters` in some other shape (e.g. `chapters.id` referenced BY `kb_nodes`)** — same effective design as the chosen FK, just inverted ownership; keeping the FK on `chapters` (not on `kb_nodes`) is simpler because `chapters` already has zero rows with any tree relationship today, so there's no existing invariant to preserve on the `kb_nodes` side.
- **Integrity guard (needed, not automatic):** `folder_id`, when set, must reference a `kb_nodes` row with `category = '회차'` AND matching `work_id` — otherwise a chapter could point at an unrelated folder (e.g. an `인물` folder). Enforce this at the Server-Action layer (mirroring `lib/chapters/actions.ts`'s existing `assertWorkOwnership` pattern), not a DB CHECK (Postgres CHECK constraints can't reference another table's row). Example:
```typescript
async function assertChapterFolder(supabase: SupabaseClient, { workId, folderId }: { workId: string; folderId: string }) {
  const { data } = await supabase.from('kb_nodes').select('id')
    .eq('id', folderId).eq('work_id', workId).eq('category', '회차').eq('node_type', 'folder')
    .is('deleted_at', null).maybeSingle();
  return Boolean(data);
}
```
- **Cascade-safety on folder delete:** deleting a custom 회차 sub-folder (via existing `deleteNode`/`soft_delete_kb_node`) must not orphan chapters pointing at it. Since `folder_id = NULL` already means "at 회차 root" (a valid, always-correct state), the simplest non-destructive fix is to null out `folder_id` for any chapter referencing the deleted folder, in the same call:
```sql
-- inside soft_delete_kb_node, or a wrapping Server-Action step, before/after the soft-delete:
update chapters set folder_id = null where folder_id = p_node_id;
```
This means no "folder not empty, cannot delete" blocking dialog is needed — deleting a 회차 sub-folder just moves its chapters back to the root view, matching D-16/deferred-drag-move's spirit (no chapter-move UI needs to exist; falling back to root is always valid).

### §4. Folding 회차 into the KB tree — UI-layer merge, not a schema merge

`chapters` stays its own table (D-05) — the tree does not literally contain `chapters` rows as `kb_nodes`. Instead, the tree-rendering layer must **merge two data sources for display only**:
```typescript
// New: fetch chapters grouped by folder_id alongside the KB tree, for the same work
const chapters = await listChapters(supabase, { ownerId, workId }); // existing lib/chapters/actions.ts, unchanged
// Walk the built work tree; for every node with category === '회차', attach chapters
// whose folder_id matches that node's id (or, for the 회차 root node itself, chapters
// with folder_id === null) as synthetic leaf entries — NOT real kb_nodes rows.
```
- Synthetic chapter leaves need a distinguishing shape from `TreeNode` (e.g. `{ kind: 'chapter', id, title, isPublished }` vs. `{ kind: 'node', ...TreeNode }`) so `KbTree`'s renderer can route clicks to `/studio/${workId}/chapters/${chapterId}` (existing chapter editor route) instead of `/studio/${workId}/kb/${nodeId}`.
- The 회차 root folder and its sub-folders must **not** offer the existing "새 문서 만들기" (create KB file) action — replace with "새 회차 만들기" (navigates to `/studio/${workId}/chapters/new`, ideally pre-selecting the clicked folder — requires extending `chapters/new`'s form with a folder picker, see §3) and "새 하위 폴더" (create custom sub-folder, reuses `createNode` with `nodeType: 'folder'`, category inherited as `'회차'`).
- `ChaptersNavLink` (the current pinned separate link) becomes redundant once 회차 lives in the tree — recommend removing it and instead making the 회차 root tree row itself link to `/studio/${workId}/chapters` (list view) when clicked, while individual chapter leaves link to their editor directly. This is a UX recommendation for planning, not a locked CONTEXT decision — flag for UI-SPEC/planning confirmation if this phase gets one.

### §5. New folder-creation UI/action for KB-03

`createNode` in `lib/kb/actions.ts` **already accepts `nodeType: 'folder'`** — no change needed to the core mutation function. What's missing is purely the caller side:
1. A new dialog (`CreateFolderDialog`, sibling to the existing `CreateNodeDialog` in `kb-node-dialogs.tsx`) — no name-collision/template-picker UI needed (folders never seed content), just a name input, reusing the exact same `FRIENDLY_NAME_COLLISION` error path (the sibling-unique index already covers folders and files in the same namespace — confirmed: `kb_nodes_sibling_name_unique` has no `node_type` filter).
2. `KbTreeActions`'s existing single "+" button (currently hardcoded to open `CreateNodeDialog` only, and gated off entirely for `category === 'template'`) needs to become a small menu/two buttons: "새 문서" (existing, gated off for `template`/`회차` categories) + "새 폴더" (new, available on any non-locked... actually available on **any** folder below a root per D-02, including `template` — CONTEXT doesn't ask this phase to touch the pre-existing `template`-folder gate specifically for documents, only clarifies folders generally are allowed everywhere below root; treat "새 폴더" as available everywhere below a root, "새 문서" gating unchanged from current behavior except also excluding `회차`-category folders per D-04).
3. **New top-level folder creation** (directly under a root) has no existing `KbTreeActions`-equivalent entry point today, since no `kb_nodes` row represents the root (§2) — needs a new UI affordance near the root headers themselves (`work.title` header, "계정 공유 폴더" header), each triggering `CreateFolderDialog` with `parentId: null` and an explicit `category: 'custom'` (server-derives/validates this, does not trust client-supplied category blindly — see §1).

### §6. Cross-scope mention search for D-09/D-10

`lib/ai/mentions.ts`'s `searchMentionNodes` is currently a single query: `work_id`-scoped, `category IN KB_CATEGORIES` only. Per the existing two-query-then-merge pattern already used by `getKbTree` (`Promise.all` of two independent Supabase queries, since Supabase-js has no cross-predicate UNION), extend to:
```typescript
export async function searchMentionNodes(supabase, { ownerId, workId, query }) {
  const trimmed = query.trim();
  if (!trimmed) return [];
  const [workResults, sharedResults] = await Promise.all([
    supabase.from('kb_nodes').select('id, name, category')
      .eq('owner_id', ownerId).eq('work_id', workId).eq('scope', 'work')
      .eq('node_type', 'file').in('category', [...KB_CATEGORIES, 'custom'])
      .ilike('name', `%${trimmed}%`).is('deleted_at', null).order('name').limit(20),
    supabase.from('kb_nodes').select('id, name, category')
      .eq('owner_id', ownerId).eq('scope', 'account_template')
      .eq('node_type', 'file') // no category filter — see Open Questions on template-file mentionability
      .ilike('name', `%${trimmed}%`).is('deleted_at', null).order('name').limit(20),
  ]);
  return [...(workResults.data ?? []), ...(sharedResults.data ?? [])] as MentionCandidate[];
}
```
- D-10 (one-way only) is satisfied structurally, not by an extra filter: `sharedResults` is scoped to `owner_id` (not any other writer's account) and this function is only ever called in the context of writing inside `workId` — there's no code path where another work's `work`-scoped docs enter the result set. No new guard needed beyond what's already true of the function's call sites.
- `MentionCandidate`'s `category: KbCategory` type needs widening (`KbCategory | 'custom' | 'template'`) since results can now include those categories — a small type change, not a behavior risk.
- **Work-scoped filter change** (`[...KB_CATEGORIES, 'custom']`, was `KB_CATEGORIES` only): this is a **new inference**, not an explicit CONTEXT decision — flagged in Open Questions below for confirmation, since it changes already-shipped EDIT-01 behavior (previously custom-category docs didn't exist, so this is additive, but worth a founder sanity-check).

### §7. Migration checklist (concrete, ordered)

New file: `supabase/migrations/0004_kb_custom_folders.sql`. Contents, in dependency order:

1. Widen `category` CHECK (§1).
2. **Fix the lock regression** (D-03 re-assertion): `update kb_nodes set is_locked = true where category in ('인물','장소','사건','세력','아이템') and node_type = 'folder' and parent_id is null and deleted_at is null;` — this reverses `0002_studio.sql`'s trailing "unlock" statement's effect for all *existing* works.
3. Update `create_work()`: add `'회차'` to the category loop array, and change the `is_locked` expression from `v_category = 'template'` to `v_category in ('template','인물','장소','사건','세력','아이템','회차')` (i.e., every structural folder locked — `is_locked = true` unconditionally inside this loop, since the loop only ever iterates the 7 fixed categories).
4. Backfill 회차 folder for existing works (D-06):
```sql
insert into kb_nodes (owner_id, work_id, scope, parent_id, node_type, category, is_locked, name)
select w.owner_id, w.id, 'work', null, 'folder', '회차', true, '회차'
from works w
where w.deleted_at is null
  and not exists (
    select 1 from kb_nodes k
    where k.work_id = w.id and k.category = '회차' and k.node_type = 'folder'
      and k.parent_id is null and k.deleted_at is null
  );
```
5. Add `chapters.folder_id` + index (§3).
6. Add the "no generic KB file under a 회차-category folder" guard trigger (D-04 defense-in-depth, mirroring the existing `guard_locked_kb_node` pattern):
```sql
create or replace function guard_chapter_folder_no_kb_files() returns trigger
language plpgsql as $$
declare v_parent_category text;
begin
  if NEW.node_type = 'file' and NEW.parent_id is not null then
    select category into v_parent_category from kb_nodes where id = NEW.parent_id;
    if v_parent_category = '회차' then
      raise exception 'chapter_folder_no_kb_files';
    end if;
  end if;
  return NEW;
end;
$$;

drop trigger if exists kb_nodes_guard_chapter_folder on kb_nodes;
create trigger kb_nodes_guard_chapter_folder before insert or update on kb_nodes
  for each row execute function guard_chapter_folder_no_kb_files();
```
7. Update `soft_delete_kb_node()` (or wrap it) to null out `chapters.folder_id` on delete of the referenced folder (§3's cascade-safety) — since `soft_delete_kb_node` is `security definer`, adding one `UPDATE chapters SET folder_id = NULL WHERE folder_id = p_node_id` inside the same function body is the natural place, executed before the `kb_nodes` update so both happen in the RPC's implicit transaction.
8. `ensure_account_template_root()` needs **no functional change** given §2's decision (no new root row) — it keeps creating exactly the `template` folder it does today. Rename is optional/cosmetic only if the planner wants the function name to stop implying "the only root concept," not functionally required.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Folder/file name uniqueness among siblings | A new collision-check query before insert | Existing `kb_nodes_sibling_name_unique` index + `error.code === '23505'` → `FRIENDLY_NAME_COLLISION` mapping in `createNode`/`renameNode` | Already generic across `node_type`, already tested (`document-crud.test.ts`), zero new code needed for folders |
| Locked-folder protection | New app-level "is this locked?" check before every mutation | Existing `guard_locked_kb_node()` DB trigger — just seed the new 회차 folder (and re-locked category folders) with `is_locked = true`; the trigger already fires on any `UPDATE` | Defense-in-depth already proven at both the Server-Action layer (returns friendly error) and DB layer (trigger raises regardless of caller) |
| Tree nesting/rendering | A tree component library (`react-arborist` etc., already evaluated and rejected in `02-RESEARCH.md`) | `buildTree()` (pure, arbitrary depth, already handles orphans) + the existing recursive `KbTree`/`TreeRow` components | No new depth-limit or move semantics are introduced by this phase; the existing custom recursive renderer already does everything KB-03/KB-05 need, just needs two tree instances instead of one (§2) and a synthetic-leaf merge for chapters (§4) |
| Chapter ancestry validation | A recursive "walk up parent_id to confirm this is under 회차" query, or reliance on the unused `ancestor_ids`/`depth` columns | A flat `category = '회차'` check (§3) — because category already propagates from the 회차 root through all its descendants via the same mechanism every other category uses | `ancestor_ids`/`depth` are dead columns (verified: no code populates them) — do not build new logic depending on them being correct; either populate them properly in a separate effort or ignore them, but don't half-rely on stale defaults |

**Key insight:** Every mechanism this phase needs (category propagation, sibling-uniqueness, lock-guarding, arbitrary-depth tree building) already exists in the codebase in a form general enough to reuse verbatim — the actual work is almost entirely (a) widening one CHECK constraint, (b) fixing one shipped regression, and (c) a UI-layer data-source merge for chapters. Resist the temptation to introduce a more "principled" tree model (e.g., populating `ancestor_ids` properly, introducing a real materialized-path scheme) — that's out of scope and not requested by any KB-03/04/05 decision.

## Common Pitfalls

### Pitfall 1: Breaking `tests/studio/schema-smoke.test.ts` and `tests/kb/tree-query.test.ts` silently
**What goes wrong:** Both files currently assert the *old, soon-to-be-wrong* behavior verbatim — "exactly 6 parent-less kb_nodes," "only the template folder locked," "allows renaming a non-template category folder," and `getKbTree`'s single-merged-array shape. If the plan doesn't explicitly update these, they will fail after `0004_kb_custom_folders.sql` + the `getKbTree` split land, and it will look like a regression rather than an expected, deliberate test update.
**Why it happens:** These tests were written to encode Phase 2's *actual shipped* (buggy) behavior, not its *documented intent* (D-15) — the tests are internally consistent with the code, both are wrong relative to 04.1-CONTEXT.md's D-03.
**How to avoid:** Include explicit tasks to update both files as part of this phase's plan — add the `회차` category to the expected-7 assertion, flip the lock-expectation test to expect `is_locked = true` for all 6+1 categories, and split the `getKbTree` test into two (`getWorkKbNodes`/`getAccountSharedNodes`) matching §2's refactor.
**Warning signs:** CI/`npm test` red immediately after the migration lands, with failure messages that look like "expected 6, got 7" — this is expected and should be treated as a required update, not a regression to work around.

### Pitfall 2: Trusting client-supplied `category` on new-folder creation
**What goes wrong:** If the new `CreateFolderDialog`/Server Action simply forwards whatever `category` string the client passes (mirroring `createNode`'s existing signature, which takes `category` as a plain caller-supplied string with no server-side derivation), a malicious or buggy client could create a folder with `category = '회차'` directly under a custom folder, giving it artificial lock-adjacent significance it shouldn't have (e.g. suddenly blocking KB file creation inside it per §7's guard trigger, or making it show up in chapter-folder pickers per §3's `category = '회차'` check).
**Why it happens:** `createNode` was designed for Phase 2's fixed, pre-known category set where the caller (UI) always had a legitimate category value in hand; that assumption breaks once arbitrary custom folders exist.
**How to avoid:** The new folder-creation path should **derive** category server-side from the resolved parent node's own `category` (or `'custom'` if `parentId` is null/root), never trust a client-supplied category for folder creation. `createNode`'s existing `category` parameter can stay as-is for *document* creation (where the UI already only ever offers the parent's real, known category), but a new thin wrapper for folder creation should look up `parent_id`'s category itself.
**Warning signs:** A custom folder mysteriously appearing "locked-adjacent" (blocking file creation) or showing up in a chapter-folder dropdown despite having a normal, non-회차 name.

### Pitfall 3: 회차 root folder backfill running for soft-deleted or zero-owner-mismatch works
**What goes wrong:** The backfill INSERT (§7 step 4) must filter `works.deleted_at is null` (already included above) — omitting it would create orphaned 회차 folders for deleted works, which then show up if a work is ever "undeleted" (no such feature exists today, but the `kb_nodes` RLS policy already filters `deleted_at is null` universally, so a stray folder for a deleted work is invisible but wastes a row — low severity, still worth getting right the first time since this is a one-shot backfill, not something easily corrected later without another migration).
**How to avoid:** Copy the `where w.deleted_at is null` clause exactly as shown in §7; don't drop it for "simplicity."

## Open Questions

1. **Should work-local mentions also include the new `'custom'` category (§6's `[...KB_CATEGORIES, 'custom']`)?**
   - What we know: D-09/D-10 explicitly scope the *new* mentionability decisions to the account-shared → work direction only; they say nothing about whether a work's own newly-possible custom-folder documents should be mentionable within that same work.
   - What's unclear: whether excluding `'custom'`-category work-local docs from mentions was an intentional omission or simply not considered, since custom top-level work folders didn't exist before this phase.
   - Recommendation: Default to **including** `'custom'` in work-local mention search (as shown in §6) — the least-surprising behavior for a writer who just created a custom folder and expects to `@`-mention what's inside it, consistent with EDIT-01's generic "KB documents" framing. Confirm with the founder during planning if this default feels wrong; low cost to flip either way (single array literal).

2. **Does D-09's "documents anywhere inside 계정 공유 폴더... not just template" mean `template`-category files themselves become mentionable cross-work?**
   - What we know: the literal text explicitly says "not just template," which most naturally reads as "template folder's contents are included, and so are custom folders' contents" — i.e., the account-shared `template/` folder's stub files (`인물`, `장소`, etc. — canonical template text, not real story content) would become `@`-mentionable from any work once this ships, per §6's no-category-filter query.
   - What's unclear: whether the founder intended template *stub* files (reusable document skeletons, not narrative content) to be injectable as AI-generation context via `@`-mention — this is a genuine, slightly odd UX outcome (mentioning "인물" would surface both real character documents AND the literal 인물 template stub).
   - Recommendation: Implement per the literal reading (§6, no category filter on account-shared mention search) since that's what D-09's text supports, but flag this specifically for a quick founder confirmation before/during planning — it's a one-line filter change (`.in('category', ['custom'])` to exclude `template`) if the answer is "no, exclude template."
