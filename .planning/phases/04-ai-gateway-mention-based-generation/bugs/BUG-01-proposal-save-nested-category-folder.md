# BUG-01: 하위 폴더가 있는 카테고리에서 AI 문서 제안 저장·빠른 추가 실패

## 증상

AI 패널에서 문서 제안의 **"문서로 저장하기"** 를 누르면 토스트 `카테고리 폴더를 찾을 수 없어요.`가 뜨고 문서가 만들어지지 않는다.
같은 함수를 쓰는 **@멘션 빠른 추가(QuickAddDialog)** 도 같은 카테고리에서 똑같이 실패한다.

## 재현

1. 작품의 카테고리 폴더 안에 하위 폴더를 만든다. 예: `인물` → `서브인물`
2. 챕터 편집기 AI 패널에서 "이 이야기에 어울리는 새 인물 설정 문서를 하나 제안해줘"를 보낸다.
3. 응답의 `[인물] …` 제안 아래 **문서로 저장하기**를 누른다.

재현된 작품: `버그 재현용 작품` (`e33f73fb-c36f-402e-9f20-1622aa04a01f`). 이 작품에는 카테고리가 `인물`인 폴더가 두 개 있다.

| name | category | root |
|---|---|---|
| 인물 | 인물 | true |
| 서브인물 | 인물 | false |

## 기대 / 실제

- **기대(AI 문서 제안):** Jev가 사용자 요청과 작품 문맥을 바탕으로 필요한 작업, 문서 카테고리, 저장 폴더와 템플릿을 먼저 결정한다. Gemini는 선택된 템플릿과 제공된 작품 정보를 따라 문서를 생성한다. 사용자는 생성 결과와 저장 위치를 확인하고 변경할 수 있으며, 확정한 폴더에 저장된 뒤 "문서로 저장됨 ✓"로 바뀐다.
- **기대(@멘션 빠른 추가):** 빠른 추가 대화상자에서 같은 카테고리의 실제 폴더 중 저장 위치를 직접 선택할 수 있고, 선택한 폴더에 문서가 생성된다.
- **실제:** `{ ok: false, error: '카테고리 폴더를 찾을 수 없어요.' }`가 반환되고 문서가 생성되지 않는다.

## 원인

`lib/ai/mentions.ts`의 `resolveCategoryFolderId`는 같은 작품·같은 카테고리의 폴더가 **정확히 하나**라고 가정하고 `.maybeSingle()`로 조회한다.

```ts
.from('kb_nodes').select('id')
  .eq('owner_id', ownerId).eq('work_id', workId)
  .eq('category', category).eq('node_type', 'folder')
  .is('deleted_at', null)
  .maybeSingle();
```

하위 폴더도 부모와 같은 `category` 값을 가지므로 두 행이 나오고, `maybeSingle`이 에러를 반환한다. 결국 `data`가 null이 되어 함수가 `null`을 돌려준다.

호출 경로:
- `quickAddMentionNode` (lib/ai/mentions.ts:83)
  - `quickAddMentionAction` (actions.ts:75)
  - 제안 저장 액션 (actions.ts:164)

## 해결 설계 (2026-09-22 결정)

단순히 `parent_id IS NULL` 조건을 추가해 모든 문서를 최상위 카테고리 폴더에 저장하는 방식은 채택하지 않는다. 이 방식은 저장 실패만 막을 뿐, 하위 폴더를 쓰는 사용자가 생성 후 매번 문서를 직접 이동해야 하므로 UX가 나쁘다.

기존의 `Gemini 문서 생성 → Jev 위치 분류` 순서도 채택하지 않는다. 생성 모델이 문서 종류와 형식을 자유롭게 결정한 뒤 위치만 분류하면 기존 템플릿을 생성 품질에 활용할 수 없고, 결과물 형식도 일관되지 않기 때문이다.

문서 생성 전에 Jev가 **작업 계획**을 정하고, Gemini는 확정된 계획에 따라 템플릿을 채우도록 순서를 바꾼다.

1. **서버가 판단 문맥을 구성한다.** 사용자의 마지막 요청, 세션 대화, 현재 챕터 본문, 멘션된 KB 문서와 실제 선택 후보를 준비한다.
2. **Jev가 작업과 카테고리를 결정한다.** `대화 응답`, `본문 초안`, `설정 문서`, `추가 질문 필요` 중 하나와, 설정 문서인 경우 카테고리를 확률과 함께 선택한다.
3. **서버가 카테고리별 후보를 조회한다.** 같은 사용자·작품·카테고리의 활성 폴더와 작품 전용·계정 공유·기본 템플릿을 가져온다.
4. **Jev가 폴더와 템플릿을 결정한다.** 카테고리가 확정된 후보 집합 안에서 저장 폴더와 사용할 템플릿을 각각 선택한다.
5. **서버가 모든 선택을 검증한다.** Jev가 반환한 불투명 후보 키를 실제 폴더·템플릿으로 매핑하고 소유권, 작품, 범위, 삭제 상태를 확인한다.
6. **Gemini가 템플릿 기반 문서를 생성한다.** 선택된 템플릿 원문, 사용자 요청, 작품 문맥과 KB 정보를 전용 프롬프트로 전달한다. Gemini는 템플릿의 구조와 섹션을 유지하면서 제목과 내용을 채운다.
7. **사용자가 생성 결과와 계획을 확인한다.** 제안 카드에 `저장 위치`와 `사용 템플릿`을 표시하고, 저장 위치는 생성 후에도 변경할 수 있게 한다.
8. **확정한 폴더에 저장한다.** 저장 액션은 `targetFolderId`와 선택된 템플릿 정보를 받아 마지막으로 검증한 뒤 문서를 생성한다.

### 역할 경계

| 구성요소 | 책임 |
|---|---|
| Jev | 작업 종류·문서 카테고리·저장 폴더·템플릿 선택 및 후보별 확률 반환 |
| Gemini | 확정된 템플릿과 작품 문맥에 맞춰 문서 제목과 본문 생성 |
| 서버 | 후보 조회, 후보 키 매핑, 템플릿 전달, 소유권·작품·카테고리·삭제 상태 검증 |
| 사용자 | 생성 결과·저장 위치·사용 템플릿 확인 및 필요 시 변경 |

Jev는 생성 모델을 대체하지 않는다. 자유 형식 텍스트를 만들지 않고 서버가 제공한 제한된 후보 중 작업 계획만 고르는 결정 계층으로 사용한다. 프로덕션에서는 평가한 고정 버전을 사용하고 `latest` 별칭은 사용하지 않는다.

### 기존 템플릿 시스템 재사용

새로운 템플릿 저장소를 만들지 않는다. `lib/kb/actions.ts`의 `listTemplateOptions`가 이미 다음 후보를 제공한다.

1. 작품 전용 템플릿
2. 계정 공유 템플릿
3. `docs/Template`의 기본 템플릿

`createNode`도 `templateOverrideContent`를 받아 명시적으로 선택한 템플릿을 사용할 수 있다. 현재 AI 제안 저장 경로는 `quickAddMentionNode`로 기본 템플릿을 잠깐 적용한 뒤 `saveNodeContent`로 Gemini의 자유 형식 본문을 덮어쓴다. 새 설계에서는 선택한 템플릿을 **Gemini 호출 전에** 프롬프트에 포함해 생성 결과 자체가 템플릿을 따르게 한다.

### Jev 입력 계약

Jev에는 실제 데이터베이스 ID 대신 요청마다 만든 불투명 후보 키를 보낸다. 첫 번째 판단은 작업 종류와 문서 카테고리를 결정하고, 문서 카테고리가 확정된 뒤 두 번째 판단에서 해당 카테고리의 폴더와 템플릿만 제공한다.

```json
{
  "state": {
    "userRequest": "주인공의 오랜 친구이자 사건의 목격자인 인물을 만들어줘",
    "chapterContext": "비가 그친 뒤 주인공은 낯익은 목소리를 들었다...",
    "mentionedFacts": ["오수진은 주인공의 학창 시절 친구다"],
    "folderCandidates": [
      {
        "key": "folder_1",
        "path": "인물",
        "description": "분류되지 않은 인물 문서"
      },
      {
        "key": "folder_2",
        "path": "인물/주요 등장인물",
        "description": "주요 인물과 핵심 관계"
      }
    ],
    "templateCandidates": [
      {
        "key": "template_1",
        "name": "작품 전용 주요 인물 템플릿",
        "scope": "work",
        "outline": ["기본 정보", "성격", "배경", "인물 관계"]
      },
      {
        "key": "template_2",
        "name": "기본 인물 템플릿",
        "scope": "canonical",
        "outline": ["기본 정보", "외형", "성격", "서사 역할"]
      }
    ]
  }
}
```

- 작업 후보에는 `reply`, `draft`, `document`, `clarify`를 반드시 포함한다. 요청이 모호하면 억지로 문서 종류를 고르지 않고 `clarify`를 선택할 수 있어야 한다.
- 문서 카테고리 후보에는 다섯 고정 카테고리와 `clarify`를 포함한다.
- 폴더는 경로 기준, 템플릿은 범위와 이름 기준으로 안정적으로 정렬해 입력 순서를 고정한다.
- Jev에는 템플릿 전체보다 이름, 범위와 섹션 개요를 우선 제공한다. 선택된 템플릿의 전체 원문은 Gemini에 전달한다.
- 폴더 설명이 존재한다면 함께 보내되, 다른 폴더 안의 기존 문서 본문은 보내지 않는다.
- 챕터 전체가 지나치게 길면 마지막 관련 구간과 멘션된 핵심 사실을 우선 사용하고, 실제 평가로 입력 길이를 결정한다.
- 한국어 원문과 한국어 폴더 경로를 그대로 사용한다. 별도 영문 번역 단계는 두지 않는다.

### Gemini 생성 계약

Gemini에는 일반적인 `[DOCUMENT]` 요청만 주지 않고 선택된 계획을 명시한 전용 생성 지시를 제공한다.

```text
작업: 설정 문서 생성
카테고리: 인물
저장 목적: 주요 등장인물 설정
대상 폴더: 인물/주요 등장인물

아래 템플릿의 제목·섹션 구조와 순서를 유지하면서 내용을 채우세요.
사용자 요청, 현재 챕터와 KB에 없는 사실을 임의로 확정해야 한다면 명시적으로 미정으로 남기세요.

템플릿:
# <% tp.file.title %>

## 기본 정보
...
```

- Gemini는 선택된 카테고리와 템플릿을 바꾸지 않는다.
- 템플릿의 필수 제목과 섹션은 삭제하거나 이름을 바꾸지 않는다.
- 알려진 KB 사실과 모순되는 내용을 만들지 않는다.
- 근거가 부족한 필드는 빈 값 또는 `미정`으로 남긴다.
- 응답은 대화용 설명과 구조화된 문서 결과를 분리해 반환한다.
- 생성된 문서에는 `targetFolderKey`와 `templateKey`를 다시 쓰게 하지 않는다. 이 값은 서버가 Jev 결과로 보관하고 결합한다.

### 후보 및 예외 처리 규칙

- 폴더 후보는 `owner_id`, `work_id`, `scope = 'work'`, 선택된 `category`, `node_type = 'folder'`, `deleted_at IS NULL`을 모두 만족해야 한다.
- 템플릿 후보는 현재 작품 또는 같은 사용자의 계정 공유 범위에 속하거나 기본 템플릿이어야 한다.
- 폴더나 템플릿 후보가 하나뿐이면 해당 항목에 대한 Jev 판단을 생략한다.
- 최상위 카테고리 폴더는 항상 안전한 `분류 안 됨` 폴더 후보로 포함한다.
- Jev가 작업·카테고리를 낮은 확신도로 판단하면 Gemini에게 문서를 생성시키지 않고 사용자에게 필요한 정보를 묻는 응답을 생성한다.
- 폴더 판단이 실패하거나 확신도가 낮으면 최상위 카테고리 폴더를 추천한다.
- 템플릿 판단이 실패하거나 확신도가 낮으면 기존 우선순위(작품 전용 → 계정 공유 → 기본)의 기본 템플릿을 사용한다.
- 확신도 임계값은 임의로 정하지 않는다. 실제 제안 데이터에 대한 사전 평가 결과로 결정하고 설정값으로 관리한다.
- 계획 결정은 자동 저장이 아니다. 실제 경로와 템플릿 이름을 UI에 표시하고 사용자가 저장 버튼을 눌러 확정하게 한다.
- 생성 후 저장 폴더 변경은 재생성 없이 허용한다. 템플릿을 변경하면 기존 결과가 새 템플릿을 따르지 않으므로 재생성 여부를 사용자에게 확인한다.
- 사용자가 확정한 뒤 폴더가 삭제·이동되었거나 권한 검증에 실패하면 다른 위치에 조용히 저장하지 않는다. `저장 위치가 변경되었어요. 다시 선택해주세요.`를 반환하고 후보를 새로 조회한다.
- 활성 최상위 카테고리 폴더 자체가 없거나 중복된 경우는 데이터 이상으로 취급한다. 임의의 하위 폴더나 오래된 폴더를 선택하지 않는다.

### @멘션 빠른 추가

빠른 추가는 Gemini가 만든 본문이 없고 사용자가 입력한 짧은 이름만 있으므로 Jev가 신뢰할 만한 위치를 판단할 근거가 부족하다. 이 경로에는 Jev를 호출하지 않는다.

- `QuickAddDialog`에 카테고리와 연동된 `저장 폴더` 선택 항목을 추가한다.
- 기본값은 해당 카테고리의 최상위 폴더로 두되, 사용자는 생성 전에 하위 폴더를 선택할 수 있다.
- 저장 액션은 AI 제안 저장과 동일한 `targetFolderId` 서버 검증을 사용한다.

### 단계적 도입

1. **오프라인 평가:** 사용자 요청과 사람이 정한 작업·카테고리·폴더·템플릿 정답 100~300건을 만들고 Jev를 평가한다. 후보 순서를 바꾼 반복 평가로 순서 민감도도 확인한다.
2. **그림자 계획:** 기존 Gemini 응답은 유지하면서 Jev가 선택했을 계획과 확률·응답시간·비용만 기록한다.
3. **템플릿 생성 비교:** 동일 요청에 자유 형식 Gemini 생성과 Jev 선택 템플릿 기반 생성을 수행해 필수 섹션 충족률, 사용자 수정량과 재생성률을 비교한다.
4. **추천 활성화:** 합의한 정확도와 확신도 보정 기준을 만족하면 Jev 계획을 실제 Gemini 프롬프트에 적용한다.
5. **운영 관측:** 계획 수락률, 폴더·템플릿 변경률, `clarify` 비율, 폴백률, 전체 P50/P95 지연시간, 호출당 비용과 재생성률을 지속 관측한다.

Jev는 새 공급자이므로 도입 전에 작품 데이터 보관, 학습 사용, 처리 지역, 삭제 정책을 확인한다. 해당 검토가 끝나기 전에는 실제 작품 본문을 프로덕션 Jev 호출에 보내지 않는다.

## 검증

- Jev 작업 계획이 Gemini 호출보다 먼저 수행되는지 테스트한다.
- 일반 대화, 본문 초안, 설정 문서, 추가 질문 필요가 각각 올바른 생성 프롬프트로 연결되는지 테스트한다.
- 문서 카테고리가 확정된 뒤에만 해당 카테고리의 폴더·템플릿 후보가 조회되는지 테스트한다.
- 같은 카테고리의 최상위·하위 폴더가 모두 후보로 조회되고, 다른 작품·사용자·카테고리·삭제 폴더가 제외되는지 테스트한다.
- 작품 전용·계정 공유·기본 템플릿이 후보에 포함되고 기존 기본 템플릿 우선순위가 유지되는지 테스트한다.
- 폴더 또는 템플릿 후보가 하나일 때 해당 Jev 판단을 생략하는지 테스트한다.
- Jev가 반환한 후보 키가 올바른 폴더·템플릿으로 매핑되는지, 알 수 없는 키가 거부되는지 테스트한다.
- 선택된 템플릿 원문이 Gemini 프롬프트에 포함되고 결과가 필수 제목·섹션을 유지하는지 테스트한다.
- Jev의 작업·카테고리 확신도가 낮으면 문서를 생성하지 않고 추가 질문 응답으로 전환되는지 테스트한다.
- 폴더 판단 실패·타임아웃·낮은 확신도에서 최상위 폴더가 추천값으로 사용되는지 테스트한다.
- 템플릿 판단 실패·타임아웃·낮은 확신도에서 기존 기본 템플릿이 선택되는지 테스트한다.
- 사용자가 추천과 다른 폴더를 선택하면 사용자 선택이 우선되는지 테스트한다.
- 사용자가 템플릿을 바꾸면 재생성 확인 절차가 동작하는지 테스트한다.
- 저장 직전 폴더가 삭제되거나 다른 작품의 폴더 ID가 전달되면 생성 없이 명확한 오류를 반환하는지 테스트한다.
- 빠른 추가에서 선택한 하위 폴더에 문서가 생성되고 즉시 검색 가능한지 테스트한다.
- 브라우저에서 선택된 템플릿·추천 경로 표시, 위치 변경, 템플릿 변경 재생성, 저장 성공 토스트를 확인한다.
- `npx vitest run tests/ai --no-file-parallelism`, `npx tsc --noEmit`, `npm run lint`를 통과시킨다.
