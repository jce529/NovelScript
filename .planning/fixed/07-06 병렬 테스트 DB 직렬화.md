# 07-06: 병렬 테스트 DB 직렬화

## 증상

`npx vitest run` 기본(파일 병렬) 실행에서 원격 Supabase를 쓰는 DB 테스트가 타임아웃/`Database error creating new user`로 약 11건 실패한다고 기록돼 있었다. 직렬 실행은 통과했다.

## 원인

원격 프로젝트를 쓰는 테스트 파일(Auth admin API로 계정 생성, PostgREST, 직접 Postgres 연결)이 동시에 몰려 부하가 집중됐다. 이 phase에서는 직접 DB 연결 8개 파일만 대상으로 보았지만 실제로는 Auth/PostgREST를 쓰는 약 48개 파일이 같은 부하를 만든다.

## 수정

- `vitest.config.ts`를 `test.projects`로 분리: `unit`(파일 병렬 유지)과 `db`(`fileParallelism: false`). 공통 `env`·alias·타임아웃(30초)은 `extends: true`로 상속. DB 프로젝트 배정은 파일 **내용** 기준(`helpers/db` import, `SUPABASE_DB_URL`·`SUPABASE_SERVICE_ROLE_KEY`·`postgres(` 사용)으로 자동 분류해 새 DB 테스트 파일이 설정 수정 없이 직렬 실행된다. Vitest 4에서 제거된 `poolOptions`는 쓰지 않았다. 타임아웃은 상향하지 않았다.
- `tests/config/vitest-projects.test.ts`: 모든 테스트 파일이 정확히 한 프로젝트에 배정되는지, DB만 직렬인지, 대표 파일 배정, 상속 설정 유지를 검증.

## 검증

- 변경 후 `npm test` 연속 실행: 113파일 1147개 전부 통과(약 214초) 2회, 그 사이 1회는 Phase 8 BUG-06 동시성 DB 테스트의 타이밍 가정 때문에 1건 실패해 그 테스트를 보정함.
- 측정 중 알게 된 점: 변경 전 기준선 실패 8~9건은 타임아웃이 아니라 같은 시점에 `deleteTestUser`가 오류를 던지도록 바꾼 탓(원장 행이 있는 계정은 삭제 불가)이었다. `deleteTestUser`는 best-effort로 되돌리고 `deleteTestUserStrict`를 따로 추가해 해결했다. 문서에 적힌 원격 타임아웃은 이번 환경에서 재현되지 않았고 시간 단축 효과는 확인하지 못했다(안정성 우선).
- 미확인: `--no-file-parallelism` 전체 직렬 실행과의 시간 비교, Phase 11 예정 `tests/ai/ai-usage-db.test.ts`의 자동 분류(`helpers/db` 사용 시 `db`로 분류됨).
