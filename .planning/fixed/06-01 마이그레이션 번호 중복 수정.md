# 06-01: 마이그레이션 번호 중복 수정

## 증상

병렬로 진행된 세 phase가 같은 번호 `0015`를 써서 `0015_author_settlement`, `0015_byok_secret_cleanup`, `0015_payments`가 공존했다. 새 환경에서는 파일명 정렬 순서로 적용 순서가 우연히 정해졌다.

## 원인

병렬 phase들이 "다음 번호"를 각자 계산했고, 적용 이력을 기록하는 테이블/스크립트가 없어 충돌이 자동으로 드러나지 않았다.

## 수정

- 원격 DB에 먼저 적용된 `0015_byok_secret_cleanup.sql`은 유지, `0015_payments.sql` → `0016_payments.sql`, `0015_author_settlement.sql` → `0017_author_settlement.sql`(`git mv`, SQL 본문 변경 0줄).
- `tests/commerce/settlement.test.ts`의 파일 참조와 Phase 5·6·11, STATE, ROADMAP, SSOT 문서의 파일명 갱신. Phase 11의 `0016_ai_usage`는 `0018_ai_usage`로 조율하고 실행 직전 번호 확인 게이트를 추가.
- 재발 방지: `tests/migrations/numbering.test.ts`가 마이그레이션 접두부의 형식·유일성을 검사한다.

## 검증

- 수정 전 가드 테스트는 중복 때문에 실패하고 재번호링 후 통과. `tests/migrations tests/commerce tests/payments` 8파일 48개 통과, `tsc` 통과.
- 이후 새 마이그레이션(0019 Phase 3, 0020 Phase 2, 0021 Phase 8)은 가드 아래 유일한 번호로 추가됨.
- 미확인: 원격 배포 경로의 마이그레이션 이력. 원격 테스트 DB에는 세 SQL이 이미 적용돼 있고 `scripts/apply-migration.mjs`는 이력을 기록하지 않아 DB 영향은 없다. 이력 테이블을 쓰는 배포 도구를 도입할 때는 파일명 변경 이력을 함께 조정해야 한다.

## 커밋
